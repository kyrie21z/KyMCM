# 建模方案设计规范

## 1. 目的

本规范用于约束 ChatGPT、Codex 或其他建模助手在编写 `START_QN.md`、`START_QN_K.md` 之前的方案设计过程，重点防止以下问题：

- 统计验证层过度设计；
- 执行工程层设计不足；
- 为追求“形式上的严谨”叠加大量高成本实验；
- 缺少依赖审计、可识别性预检、冒烟测试、异常隔离和断点复用；
- 正式运行失败后重复执行全部流程，造成算力和时间浪费；
- 验证成本与题目价值、剩余风险和竞赛预算不匹配。

本规范是**方案设计原则**，不是新的状态机、审批流或重型合同。它用于约束 START 的生成质量，但不要求为本规范额外创建 JSON、报告、审批文件或一致性证明。

---

## 2. 核心原则

### 2.1 执行可靠性优先

建模方案必须按照以下顺序设计：

```text
依赖审计
→ 可识别性与可解性预检
→ 最小冒烟测试
→ 正式运行
→ 基础结果审计
→ 按需高成本验证
```

只有前一层通过，才允许进入后一层。

不得在尚未确认模型可运行、可恢复、可复用时，直接设计大规模多重验证。

### 2.2 最小充分原则

每一项实验、验证或对照必须回答一个明确问题，例如：

- 检查数据泄漏；
- 验证模型是否可识别；
- 验证结果是否对关键参数敏感；
- 验证算法是否稳定；
- 验证正式输出是否可复算。

不得仅因为“论文通常这样做”“看起来更严谨”而增加实验。

当两个实验回答同一风险时，应优先保留：

1. 成本更低者；
2. 解释更直接者；
3. 对结论影响更大者；
4. 更容易复现者。

### 2.3 统计严谨性必须转化为执行可靠性

统计设计不能只规定：

- 折数；
- 重复次数；
- 指标数量；
- 敏感性分析数量；
- 对照模型数量。

还必须同步规定：

- 每个阶段的输入；
- 每个阶段的输出；
- 是否缓存；
- 是否可复用；
- 失败后从哪里恢复；
- 哪些结果是正式结果；
- 哪些结果只用于诊断或附加分析。

### 2.4 先证伪，再扩展

方案应优先设计低成本检查，用于尽早暴露：

- 数据口径错误；
- 维度不匹配；
- 标签泄漏；
- 约束冲突；
- 欠约束；
- 无界；
- 不可辨识；
- 数值不稳定；
- 求解规模失控；
- 运行时间超预算。

在这些问题未排除前，不得进入完整交叉验证、大规模情景分析、全量敏感性分析或重复正式求解。

### 2.5 竞赛预算约束

所有方案必须服从竞赛环境中的时间、算力和人工检查预算。

严谨性目标不是“实验越多越好”，而是：

> 在给定时间与算力下，获得足以支持论文结论的最小充分证据。

## 3. 方案设计的六个层级

### 3.1 层级 A：依赖与输入审计

正式建模前必须确认：

- 当前问题依赖哪些上游 START、RESULT 和正式输出；
- 所有依赖文件存在、可读且版本明确；
- 输入文件、字段、单位、主键和样本范围一致；
- 上游正式结果与当前方案引用一致；
- 当前方案未误用临时、旧版、dry-run 或非正式结果；
- 数据转换过程可追踪；
- 随机种子、外部求解器和关键软件版本明确。

该层只验证“输入是否可信且可用”，不得展开高成本统计实验。

### 3.2 层级 B：可识别性与可解性预检

在编写正式实验方案前，必须检查模型是否具备基本可行性。

#### 优化模型

- 决策变量、目标和约束是否定义完整；
- 是否存在明显无界或不可行风险；
- 变量和约束规模是否可接受；
- 整数变量、非线性项和情景数量是否导致规模爆炸；
- 是否存在可简化、线性化或分解结构；
- 是否能构造一个已知可行解。

#### 统计与机器学习模型

- 样本量是否支持候选特征数；
- 类别是否极度不平衡；
- 是否存在完全分离、共线性或不可识别参数；
- 分组结构是否允许目标交叉验证方案；
- 是否存在数据泄漏风险；
- 指标是否在当前样本规模下有意义。

#### 预测与时间序列模型

- 样本长度是否足够；
- 训练、验证和测试划分是否可实现；
- 是否存在未来信息泄漏；
- 频率、缺失值和异常值处理是否明确；
- 基准模型是否可建立。

#### 机理模型

- 参数是否可估计；
- 初值、边界条件和单位是否完整；
- 方程是否闭合；
- 数值求解是否稳定；
- 参数数量是否超出数据支持能力。

预检失败时，应先修改模型，不得用更多验证掩盖模型不可执行的问题。

### 3.3 层级 C：最小冒烟测试

所有正式实验前必须先运行最小冒烟测试。

冒烟测试应满足：

- 使用最小数据子集、最少情景或最短时间区间；
- 使用短求解时间或小迭代预算；
- 跑通完整的数据流；
- 生成至少一个可检查的中间结果和最终结果；
- 验证输出格式、字段和路径；
- 验证关键约束、指标或概率值可计算；
- 验证异常路径能够被捕获；
- 不追求正式精度和最终结论。

冒烟测试的目标是：

> 证明整条执行链路可以完成，而不是证明模型结论正确。

冒烟测试未通过时，不得启动正式运行。

### 3.4 层级 D：正式运行

正式运行必须明确拆分为若干可恢复阶段，例如：

```text
阶段 1：输入标准化
阶段 2：特征或候选集构造
阶段 3：模型建立
阶段 4：正式求解或训练
阶段 5：结果后处理
阶段 6：基础验证
阶段 7：附加验证
```

每个阶段必须定义：

- 输入文件；
- 输出文件；
- 成功条件；
- 失败条件；
- 是否允许重试；
- 是否允许复用；
- 依赖的上游阶段；
- 预计时间和资源。

禁止将全部流程写成一个无法恢复的单体脚本。

### 3.5 层级 E：基础结果审计

正式结果生成后，优先完成低成本、强必要性的基础审计。

通常包括：

- 输入输出数量核对；
- 主键唯一性；
- 约束满足性；
- 目标值或指标独立复算；
- 概率、比例和边界范围检查；
- 求解器状态检查；
- 结果文件可读性；
- 图表可打开；
- 论文数字与机器结果一致；
- 正式结果路径与版本唯一。

基础审计失败时，应修复正式流程，而不是继续叠加敏感性分析。

### 3.6 层级 F：高成本验证

高成本验证必须按风险触发，不得默认全部执行。

可包括：

- 多随机种子；
- 重复交叉验证；
- 样本外验证；
- Bootstrap；
- 敏感性分析；
- 稳健优化；
- 替代模型；
- 留一分析；
- 极端情景；
- 消融实验。

每项高成本验证必须说明：

1. 它要排除什么具体风险；
2. 若不执行，会影响哪条结论；
3. 预计成本；
4. 是否可以部分执行；
5. 触发条件；
6. 通过或失败后如何影响结论。

## 4. 实验分级制度

### L0：必须执行

用于保证结果基本可信和流程可交付，例如：

- 依赖审计；
- 数据口径检查；
- 可识别性或可解性预检；
- 冒烟测试；
- 正式运行；
- 关键约束验证；
- 核心结果复算；
- 必要的基准模型；
- 正式输出回读。

L0 未完成时，问题不得宣告完成。

### L1：条件触发

仅在特定风险出现时执行，例如：

- 普通 Logistic 分离时执行 Firth Logistic；
- 结果对初值敏感时执行多初值；
- 小样本不稳定时执行 Bootstrap；
- 求解器 Gap 较大时执行替代求解器或延长预算；
- 模型选择不稳定时执行模型集合敏感性；
- 关键参数来源不确定时执行局部敏感性。

L1 必须有明确触发条件。

### L2：资源允许时执行

用于增强论文说服力，但不应阻塞主交付，例如：

- 大规模多种子重复；
- 多套替代模型；
- 全参数网格敏感性；
- 全量留一分析；
- 扩展样本外测试；
- 额外消融与可视化。

L2 未执行时，应在 RESULT 中注明，而不是强制重跑正式流程。

---

## 5. 成本评估规范

每个正式方案必须在执行前估算成本。

至少估算：

- 主要模型拟合或求解次数；
- 每次拟合或求解的时间；
- 总运行时间；
- 峰值内存；
- 中间文件规模；
- 是否适合并行；
- 失败后的最坏重算成本。

对于嵌套实验，应显式计算总次数。

例如：

```text
外层 5 折 × 20 次重复
× 每折 30 个候选模型
× 2 个零值版本
= 6000 次模型拟合
```

若总成本超过预算，必须优先采取：

1. 删除不能改变结论的重复验证；
2. 将 L2 实验延后；
3. 缩小候选空间；
4. 减少嵌套层级；
5. 复用中间结果；
6. 改用更直接的验证方法。

不得仅写“允许并行、缓存和向量化”来替代真实成本评估。

---

## 6. 缓存、断点与复用规范

### 6.1 阶段产物

每个高成本阶段必须产生独立、可验证的中间产物。

例如：

```text
data/derived/preprocessed.csv
data/derived/candidate_features.parquet
data/derived/model_fit.json
data/derived/cv_predictions.csv
data/derived/validation.csv
```

### 6.2 复用条件

阶段结果只有在以下内容均未变化时才允许复用：

- 输入文件；
- 上游正式结果；
- 关键参数；
- 随机种子；
- 代码版本；
- 软件环境；
- 阶段配置。

复用机制应尽量轻量，可使用 manifest、哈希或明确的版本字段，但不得引入复杂状态机。

### 6.3 断点恢复

正式脚本应允许：

- 从最近成功阶段继续；
- 只重跑失败折、失败情景或失败参数组；
- 已成功结果不重复计算；
- 单个阶段失败不删除全部正式产物；
- 异常信息单独落盘。

### 6.4 幂等性

同一输入与配置重复执行时：

- 正式数值结果应一致；
- 已存在的合格阶段产物应复用；
- 不应重复追加相同记录；
- 不应产生冲突版本或重复文件。

---

## 7. 异常隔离规范

### 可修复工程异常

例如：

- 路径错误；
- 编码问题；
- 字体问题；
- 图形保存失败；
- 临时文件缺失；
- 可恢复的单折运行失败。

允许修复后从最近阶段继续。

### 模型或数据异常

例如：

- 数据泄漏；
- 约束冲突；
- 不可识别；
- 无界；
- 不可行；
- 标签冲突；
- 关键输入不一致；
- 正式结果无法复算。

必须停止并回到方案设计阶段，不得通过增加重复次数或敏感性分析继续。

### 资源异常

例如：

- 超时；
- 内存不足；
- 求解器规模失控；
- 中间文件过大。

应优先：

1. 缩减非必要实验；
2. 分阶段执行；
3. 使用断点；
4. 减少候选空间；
5. 更换等价高效算法。

不得在不改变方案的情况下盲目重复运行。

---

## 8. 对照模型与敏感性分析规范

### 8.1 对照模型

对照模型必须满足至少一个目的：

- 提供最低基准；
- 验证复杂模型是否真正带来增益；
- 验证结论是否依赖特定模型形式；
- 提供可解释的简单规则。

通常一个简单基准和一个主要对照已经足够。

不得为了“模型丰富”并列大量算法。

### 8.2 敏感性分析

敏感性分析只针对：

- 关键参数；
- 关键假设；
- 关键数据处理；
- 关键情景；
- 可能改变结论的模型选择。

不得对所有参数进行机械网格扫描。

敏感性分析应优先采用：

- 局部扰动；
- 少量有代表性的情景；
- 有理论依据的上下界；
- 能直接对应论文结论的指标。

### 8.3 验证停止规则

当新增实验不再改变以下内容时，应停止扩展：

- 主要结论；
- 方案排序；
- 关键参数方向；
- 风险判断；
- 论文中需要陈述的限制。

## 9. START 设计要求

START 不应只写“做哪些验证”，还必须写清“如何可靠执行”。

至少应包含以下内容：

### 9.1 最小执行链

```text
预检
→ 冒烟测试
→ 正式运行
→ 基础审计
→ 条件触发验证
```

### 9.2 阶段表

建议在 START 中简洁说明：

| 阶段 | 输入 | 输出 | 成功条件 | 失败处理 | 可复用 |
|---|---|---|---|---|---|
| 预处理 | 原始数据 | 标准化数据 | 口径检查通过 | 停止 | 是 |
| 冒烟测试 | 小样本 | 测试结果 | 全链路跑通 | 修复后重试 | 否 |
| 正式运行 | 全量数据 | 正式结果 | 求解成功 | 从本阶段恢复 | 是 |
| 基础审计 | 正式结果 | 验证表 | 核心检查通过 | 回退到对应阶段 | 是 |
| 附加验证 | 正式结果 | 敏感性结果 | 按触发条件完成 | 可降级 | 是 |

该表是推荐结构，不要求形成新的固定标题或机器合同。

### 9.3 验证分级

START 中应明确：

- L0 实验；
- L1 触发条件；
- L2 可选实验；
- 总预算；
- 当预算不足时优先删除哪些实验。

### 9.4 禁止项

START 不得：

- 默认堆叠所有常见统计验证；
- 同时要求多重嵌套验证、完整敏感性、全量留一和双重重复运行，却不估算成本；
- 只规定“必须全部成功”，不设计失败恢复；
- 用大量输出文件代替清晰的执行链；
- 把“完整复跑两次”作为默认确定性验证；
- 将高成本附加分析设置为主流程阻塞项；
- 规定不现实的总运行时间；
- 把缓存和并行仅写成一句“允许使用”，而没有阶段产物与复用规则。

## 10. ChatGPT 生成方案前的自检问题

ChatGPT 在输出正式建模方案前，应逐项回答：

1. 当前问题最小可交付结论是什么？
2. 支撑这些结论最少需要哪些实验？
3. 哪些风险必须在正式运行前排除？
4. 模型是否可识别、可行、可解？
5. 冒烟测试如何设计？
6. 正式流程可以拆成哪些阶段？
7. 哪些阶段成本最高？
8. 哪些阶段可以缓存和复用？
9. 单个阶段失败后从哪里恢复？
10. 哪些验证属于 L0、L1、L2？
11. 每项高成本验证解决什么风险？
12. 所有嵌套实验总共需要多少次拟合或求解？
13. 总成本是否符合竞赛预算？
14. 哪些验证可以在时间不足时删除？
15. 是否存在“形式上很严谨、实际上无法稳定执行”的设计？
16. 结果失败时应修改模型，还是增加验证？
17. 是否把工程问题误当成统计问题处理？
18. 是否把附加分析设成了主流程阻塞项？
19. 是否要求了无法合理保证的确定性或运行时间？
20. 方案是否能够由另一名队员独立执行和恢复？

若这些问题无法回答，方案不得直接写入 START。

---

## 11. 方案审查红旗

出现以下任一情况，应判定方案存在过度设计风险：

- 外层、内层、重复、敏感性和留一分析多重嵌套；
- 验证次数远高于正式模型求解次数；
- 输出文件数量很多，但执行阶段不清晰；
- 强制要求所有附加实验完成才能交付；
- 要求完整运行两次验证哈希一致；
- 规定严格时间预算，却没有成本计算；
- 没有冒烟测试；
- 没有断点恢复；
- 没有缓存边界；
- 没有失败隔离；
- 不区分主结论证据与附加证据；
- 对照模型数量过多；
- 所有验证都被写成“不得减少”；
- 只允许增加迭代和重试，不允许削减非必要实验。

## 12. 推荐的方案设计流程

```text
第一步：明确最小交付
第二步：识别关键风险
第三步：设计依赖与可解性预检
第四步：设计最小冒烟测试
第五步：拆分正式执行阶段
第六步：定义阶段产物、缓存和恢复
第七步：完成基础审计
第八步：只为剩余风险设计验证
第九步：对实验进行 L0/L1/L2 分级
第十步：计算总运行成本
第十一步：削减不能改变结论的实验
第十二步：再写入 START
```

## 13. 完成标准

一份合格的建模方案应同时满足：

1. 模型在理论上可识别、可行或可解；
2. 最小冒烟测试可执行；
3. 正式流程分阶段；
4. 每个高成本阶段有明确产物；
5. 支持断点恢复；
6. 支持合格结果复用；
7. 工程异常和模型异常能够隔离；
8. L0、L1、L2 验证边界清晰；
9. 总运行成本经过显式估计；
10. 方案在竞赛预算内可完成；
11. 统计验证与论文结论直接对应；
12. 不通过堆叠实验掩盖基础执行问题。

最终原则：

> 先保证模型能够正确运行、失败后能够恢复、已有结果能够复用，再通过最小充分的统计验证支撑论文结论。
