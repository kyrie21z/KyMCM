## Modeling-plan design and execution

Before authoring, materially revising, reviewing, or executing any selected START, read `references/modeling_plan_design.md` completely. Apply it proportionally: define the minimum paper-ready deliverable; audit dependencies and inputs; preflight identifiability, feasibility, boundedness, numerical meaning, and computational solvability; design the smallest end-to-end smoke test; split formal work into recoverable stages with inspectable artifacts and exact cache/reuse conditions; estimate nested fit/solve/scenario count, runtime, memory, parallelism, and worst-case recomputation; then classify experiments as mandatory L0, condition-triggered L1, or resource-permitting L2.

Run work in this order: author the START, run `check-start`, complete the separate dependency contradiction review, complete the final modeling-plan design review, pass the minimal smoke test, execute formal stages, pass the basic/L0 result audit, run L1 only when its named risk trigger occurs, and run L2 only when resources permit and it can improve the paper. A failed smoke test blocks formal execution. A failed basic audit returns to the responsible stage rather than triggering more validation. Appendix organization uses frozen formal results and never reruns modeling experiments.

When the plan is proportionate and executable, continue without creating review state, approval, JSON, hash, report, or other success artifact. Repair deterministic engineering omissions such as missing smoke-test or checkpoint boundaries transparently in the current START, then rerun `check-start` and both semantic reviews. If resolution changes mathematical assumptions, validation strength, success criteria, or a material resource tradeoff, name the exact START section and consequence, ask one highest-impact user question, and stop. If the model is unidentifiable, infeasible, unbounded, unsupported by the data, or irreconcilable with the budget, return to model/plan design instead of adding validation or blind retries.

Preserve mathematical meaning, parameters, constraints, decision rules, data semantics, budgets, and fallback rules. Choose implementation details independently only when they cannot alter conclusions. Ask one highest-impact question and stop when semantic uncertainty remains. Stop when a discovered data issue changes values, missingness, sample membership, pairing, or model input. Repair parser, path, syntax, cache, logging, and plotting mechanics locally when semantics do not change.

Disclose every authorized START deviation in RESULT. Never create Full JSON artifacts, workflow state, approvals, events, review hashes, or content-level JSON. Never self-approve mathematical conclusions.
